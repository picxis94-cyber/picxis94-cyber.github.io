写代码第十年，我慢慢明白了一件事：**好的代码和好的诗，是同一件事。**

诗把千言万语压进几行；好的函数把一个复杂概念压缩成一个清晰的签名。诗讲究节奏和留白；好的代码讲究命名和空行。诗不写废话；好的代码里没有一句多余的注释。

```python
# 诗：
#   def life(**choices):
#       for tomorrow in days:
#           if love in choices:
#               return we(together)
```

## 命名是诗人最锋利的刀

> 命名是编程里最难的三件事之二，另外两件是缓存失效和命名。

给一个变量取名，本质是"给概念下定义"。`data`、`temp`、`x1` 是偷懒的韵脚；`revenue`、`pendingQueue`、`lastPingAt` 才是精心打磨的句子。写不出好名字，往往不是词汇量的问题，是你根本没想清楚这个概念是什么。

## 留白：注释该删就删

最好的注释是**不需要的注释**——代码本身已经说清楚了。真正值得留的注释，只有三类：

1. "为什么"（不是"是什么"）：`// 必须晚于 DNS 刷新，否则证书校验失败`
2. 复杂算法的出处：`// 见 Knuth Vol.3 §5.2.4`
3. 业务上的"陷阱警示"：`// 此处勿动，动了会全公司一起崩`

其余的，都是噪音。删除它们，代码的呼吸就通畅了。

## 重构：修改诗句，不改诗意

诗歌和代码都不怕改，怕的是**改的时候不知道在改什么**。测试就是代码的"定稿存档"——改了韵脚，意思还在：

```js
// 重构前：三行 if 塞在业务代码里
function ship(order) {
  if (!order.paid) throw new Error('未支付');
  if (order.items.length === 0) throw new Error('空订单');
  // ... 50 行发货逻辑
}

// 重构后：校验是诗的开篇，业务是诗的正文
function ship(order) {
  assertPayable(order);
  // ... 50 行发货逻辑
}
```

## 写给十年后

所以，写给十年后仍在写代码的自己：

> 别急着追求"炫酷"的架构，先写好每一行会说话的诗。函数短一点，名字准一点，逻辑诚一点。
>
> 十年后你回头看，那些让你骄傲的不是哪个框架，而是你把"用户下单"这件事，写得像一首流畅的绝句。

写代码的人很多，会写诗的代码很少。愿你的代码，读起来像诗，跑起来像闪电。
